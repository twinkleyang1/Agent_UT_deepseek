# 长时间运行 Agent 编写规范

## 一、核心挑战

长时间运行 Agent 面临三大核心问题：

| 问题 | 表现 | 解决方案 |
|------|------|----------|
| **试图一次做太多事情** | 一次性完成整个项目，耗尽上下文，下一个会话面对的是未完成且无文档的功能 | 增量工作，每个会话只处理一个功能 |
| **过早宣布完成** | 构建部分功能后，环顾四周就直接宣布完成 | 功能列表 + 独立评估器 |
| **自我评估偏差** | Agent 倾向于充满自信地赞扬自己的工作，即使质量平庸 | 执行与评估分离，由独立的评估器评分 |

---

## 二、解决方案架构

### 2.1 核心洞察

受生成对抗网络（GANs）的启发，引入**生成器（Generator）**和**评估器（Evaluator）**的多智能体结构。

```
┌─────────────────────────────────────────────────────┐
│                  单智能体的问题                      │
├─────────────────────────────────────────────────────┤
│  - 上下文窗口填满时失去连贯性                        │
│  - 上下文焦虑：接近极限时过早结束工作                │
│  - 自我评估偏差：总是对自己的工作打分过高            │
└─────────────────────────────────────────────────────┘

                    ↓ 解决方案

┌─────────────────────────────────────────────────────┐
│                 多智能体架构                         │
├─────────────────────────────────────────────────────┤
│  生成器 (Generator)  ←──→  评估器 (Evaluator)       │
│  执行工作                    评判工作               │
│  接受反馈                    提供具体迭代目标       │
└─────────────────────────────────────────────────────┘
```

### 2.2 上下文重置 vs 压缩

| 机制 | 说明 | 优缺点 |
|------|------|--------|
| **压缩 (Compaction)** | 在原地总结对话前半部分，同一个智能体继续运行 | 保留连续性，但没有"白纸"，上下文焦虑依然存在 |
| **上下文重置 (Context Reset)** | 完全清空上下文，启动新智能体，通过结构化交接传递状态 | 提供干净开局，代价是增加编排复杂性和 Token 开销 |

**结论**：对于表现出强上下文焦虑的模型（如 Sonnet 4.5），上下文重置是必要的；对于 Opus 4.5，可以依靠自动压缩处理上下文增长。

## 三、多智能体架构

### 3.1 三智能体系统

```
┌─────────────────────────────────────────────────────┐
│  规划器 (Planner)                                     │
│  - 将简单的 1-4 句话提示扩展为完整产品规格            │
│  - 关注产品背景和高层次技术设计                      │
│  - 寻找 AI 功能融合的机会                            │
│  - 不预先指定细化技术细节                            │
└─────────────────────────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────┐
│  生成器 (Generator)                                   │
│  - Sprint 式工作，每次实现一个功能                   │
│  - 自我评估后再移交                                  │
│  - 使用 Git 版本控制                                │
└─────────────────────────────────────────────────────┘
                          │
                          ▼
┌─────────────────────────────────────────────────────┐
│  评估器 (Evaluator)                                  │
│  - 使用 Playwright MCP 工具进行端到端测试           │
│  - 像真实用户一样点击运行应用程序                    │
│  - 对每个 Sprint 评分，有硬性及格线                  │
│  - 发现 Bug 时生成器 获得详细反馈                   │
└─────────────────────────────────────────────────────┘
```

### 3.2 Sprint 契约 (Sprint Contract)

在编写任何代码之前，生成器和评估器协商"完成定义（Done）"：

```
┌─────────────────────────────────────────────────────┐
│  Sprint 契约流程                                     │
├─────────────────────────────────────────────────────┤
│  1. 生成器提出将构建什么及如何验证成功               │
│  2. 评估器审查提案，确保构建了正确的东西             │
│  3. 两者反复迭代直到达成一致                        │
│  4. 生成器根据商定的契约 进行代码构建                │
│  5. 完成后移交 QA                                   │
└─────────────────────────────────────────────────────┘
```

**通信方式**：通过文件处理——一个智能体写入文件，另一个读取并回复。

## 四、环境管理

### 4.1 必要组件

| 文件 | 用途 |
|------|------|
| `init.sh` | 可直接运行开发服务器的脚本 |
| `claude-progress.txt` | 记录智能体所做工作的进度说明 |
| `feature_list.json` | 包含所有功能要求的结构化文件 |

### 4.2 init.sh 示例

```bash
#!/bin/bash
# 初始化开发环境
npm install
npm run dev
```

### 4.3 进度文件格式

```
# claude-progress.txt

## 已完成
- 用户注册功能
- JWT 认证

## 进行中
- WebSocket 实时消息

## 待完成
- 文件上传功能
- 邮件通知
```

## 五、功能列表 (Feature List)

### 5.1 JSON 格式

```json
{
  "category": "functional",
  "description": "New chat button creates a fresh conversation",
  "steps": [
    "Navigate to main interface",
    "Click the 'New Chat' button",
    "Verify a new conversation is created",
    "Check that chat area shows welcome state",
    "Verify conversation appears in sidebar"
  ],
  "passes": false
}
```

### 5.2 规则

- 初始状态所有功能标记为 `passes: false`
- 编码智能体只能通过更改 `passes` 字段来编辑此文件
- **禁止删除或编辑测试**，因为这可能导致功能缺失或 bug
- 使用 JSON 而非 Markdown，因为模型不太可能不当修改

### 5.3 功能拆分原则

- 每个功能包含具体的端到端测试步骤
- 功能描述清晰，可直接执行验证
- 功能之间相互独立

## 六、增量进展 (Incremental Progress)

### 6.1 核心原则

**每个会话只处理一个功能**

这解决了"试图一次做太多事情"的问题。

### 6.2 会话流程

```
┌─────────────────────────────────────────────────────┐
│  编码智能体会话开始                                 │
├─────────────────────────────────────────────────────┤
│  1. 运行 pwd 查看工作目录                           │
│  2. 阅读 Git 日志和进度文件了解最近工作             │
│  3. 阅读功能列表，选择未完成且优先级最高的功能       │
│  4. 运行 init.sh 启动开发服务器                     │
│  5. 运行基本端到端测试验证环境状态                   │
│  6. 选择一个功能开始工作                            │
│  7. 完成后提交 Git commit 并更新进度文件             │
└─────────────────────────────────────────────────────┘
```

### 6.3 保持环境干净

在离开会话前：
- 提交 Git commit（包含描述性提交信息）
- 更新 `claude-progress.txt`
- 确保无重大 bug
- 确保代码井然有序且有文档

### 6.4 Git 使用

```bash
# 提交进度
git add .
git commit -m "feat: 实现用户注册功能

- 添加 UserService 和 UserController
- 实现 JWT 认证流程
- 添加单元测试

Progress: 3/20 features complete"
```

## 七、评估标准

### 7.1 设计质量标准（前端设计）

| 标准 | 说明 | 权重 |
|------|------|------|
| **设计质量 (Design quality)** | 是否感觉是连贯整体而非零件拼凑？颜色、排版、布局、图像是否结合创造独特氛围？ | 高 |
| **原创性 (Originality)** | 是否有定制决策的证据？未修改的库存组件或明显 AI 生成迹象是不及格的 | 高 |
| **工艺 (Craft)** | 技术执行：排版层级、间距一致性、色彩和谐度、对比度。这是能力检查 | 正常 |
| **功能性 (Functionality)** | 独立于美学的可用性：用户能理解界面功能、找到主要操作并完成任务吗？ | 正常 |

### 7.2 软件开发评分标准

| 标准 | 及格线 | 说明 |
|------|--------|------|
| **产品深度** | 硬性及格 | 功能完整且有深度，不是表面实现 |
| **功能性** | 硬性及格 | 所有功能按预期工作 |
| **视觉设计** | 硬性及格 | 界面美观，符合设计原则 |
| **代码质量** | 硬性及格 | 代码整洁、可维护 |

### 7.3 评估器调优

- 使用少样本（few-shot）示例对评估器进行校准
- 确保评估器的判断符合预期偏好
- 减少跨迭代的分数漂移
- 设定明确的硬性及格线，任何一项低于标准则 Sprint 失败

## 八、测试策略

### 8.1 常见失败模式

Claude 倾向于在没有进行适当测试的情况下将功能标记为"完成"。

### 8.2 解决方案

| 工具 | 用途 |
|------|------|
| Playwright MCP | 浏览器自动化，端到端测试（推荐） |
| Puppeteer MCP | 浏览器自动化测试 |
| Selenium | Web 应用自动化测试 |
| curl | API 端点测试 |

### 8.3 评估器测试流程

```
┌─────────────────────────────────────────────────────┐
│  评估器测试流程                                      │
├─────────────────────────────────────────────────────┤
│  1. 评估器导航到实时页面                             │
│  2. 截图并仔细研究实现                              │
│  3. 对每个标准打分并编写详细批评                    │
│  4. 反馈流回生成器作为下一次迭代输入                 │
└─────────────────────────────────────────────────────┘
```

### 8.4 测试要求

- **必须像人类用户一样进行端到端测试**
- 不能仅依赖单元测试或代码审查
- 视觉理解有限，需要辅助工具识别 bug
- 每个循环都需要花费物理时间（完整的运行时间可长达 4 小时）

## 九、快速进入状态 (Getting Up to Speed)

### 9.1 标准流程

每个编码智能体在开始时必须执行：

```bash
# 1. 查看当前目录
pwd

# 2. 阅读进度文件
cat claude-progress.txt

# 3. 阅读功能列表
cat feature_list.json

# 4. 检查 Git 历史
git log --oneline -20

# 5. 启动开发服务器
./init.sh

# 6. 运行基本测试验证环境
```

### 9.2 时间节省

这些步骤为每个会话节省大量 token，因为：
- 不必猜测之前发生了什么
- 清楚地知道要做什么
- 立即识别应用是否损坏

## 十、失败模式与解决方案

### 10.1 问题汇总表

| 问题 | 解决方案 |
|------|---------|
| Claude 过早宣布整个项目完成 | 设置功能列表文件；每个会话开始时读取；仅选择一个功能工作 |
| Claude 将环境置于混乱状态 | 编写初始 Git + 进度文件；通过读取进度文件和 Git 开始会话；运行基本测试；以 Git commit 结束 |
| Claude 过早标记个别功能完成 | 设置功能列表；独立评估器验证所有功能；仔细测试后才标记为 passing |
| Claude 花大量时间弄清楚如何运行应用 | 编写 init.sh 脚本；会话开始时读取并运行 |
| Claude 上下文窗口填满失去连贯性 | 上下文重置 + 结构化交接 |
| Claude 上下文焦虑而过早结束工作 | 对于强焦虑模型使用上下文重置；Opus 4.5 可用自动压缩 |
| 自我评估偏差 | 执行与评估分离，独立的评估器持有怀疑态度 |

## 十一、成本与质量权衡

### 11.1 多智能体 vs 单智能体

| 指标 | 单智能体 (Solo) | 多智能体 Harness |
|------|-----------------|------------------|
| **成本** | 基准 | 高出 20+ 倍 |
| **输出质量** | 初始看似符合预期，深入交互后问题暴露 | 功能完整、稳定可用 |
| **Bug 率** | 高（崩溃、功能失效） | 低（评估器端到端验证） |
| **适用场景** | 简单任务 | 复杂长期运行任务 |

### 11.2 迭代策略

- 如果分数趋势良好则进一步完善当前方向
- 如果当前方法不奏效，则转向完全不同的方法
- 5-15 次迭代通常能达到满意结果

## 十三、总结

### 13.1 关键规则

1. **执行与评估分离** - 生成器执行工作，评估器评判工作
2. **上下文管理** - 根据模型特性选择压缩或重置
3. **Sprint 契约** - 代码编写前先商定"完成定义"
4. **功能列表驱动** - 所有功能在 JSON 中跟踪，只能更改 passes 字段
5. **增量工作** - 每个 Sprint 只处理一个功能
6. **端到端测试** - 使用 Playwright 等工具，像用户一样测试
7. **保持环境干净** - Git commit + 进度文件记录状态
8. **快速进入状态** - 标准化的会话开始流程
9. **评估器调优** - 少样本示例校准，减少分数漂移
10. **硬性及格线** - 任何标准低于及格线则判定失败

### 13.2 检查清单

```
□ init.sh 可直接运行开发服务器
□ claude-progress.txt 记录完整进度
□ feature_list.json 包含所有功能
□ 所有功能初始状态 passes: false
□ 每个 Sprint 只选择一个功能工作
□ Sprint 契约在代码编写前已达成一致
□ 评估器进行端到端测试
□ 结束前提交 Git commit
□ 更新 claude-progress.txt
□ 运行基本测试验证环境
□ 无重大 bug，代码整洁
□ 所有评估标准达到硬性及格线
```
